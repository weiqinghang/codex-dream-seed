## 1. 产品定义

Dream Console 是**有限改进承诺的闭环驾驶舱**。它帮助用户在有限容量内选择值得尝试的实践、
看见正在兑现的承诺、处理阻塞和到期事项，并由人形成可追溯的最终结论。

Console 保持确定性边界：

- 不调用模型，不在浏览器内做语义分析。
- 不直接修改项目、知识载体或用户环境。
- 语义分析、方案生成和实际执行交给 Codex/Dream。
- Console 只展示事实、计算可解释的容量与到期信号、记录人的决定，并通过可领取的 handoff
  接续 Codex。
- 已确认不等于已落实，handoff 完成不等于已验证，失败结论也不等于目标载体已经回滚。

## 2. 改进承诺与活动 WIP

### 2.1 计数单位

一个**用户已确认且正在落实或验证的实践试用承诺**占用 `1` 个活动 WIP。

- 从用户确认试用计划时开始占用，而不是从候选产生、Codex claim 或首条验证证据出现时开始。
- 同一承诺的计划或验证合同调整版本仍计为 `1`，历史版本和证据必须保留。
- 不同假设或不同适用范围被并行试验时，各自计为一个独立承诺；不能借“调整版本”合并计数。
- 候选 Inbox、待用户决定的事项和明确暂缓的候选不占活动 WIP。
- 已完成、已结束或已验证回滚的终态不占活动 WIP。
- handoff 失败、到期未决定、等待人收尾的承诺仍然占用 WIP；不能靠换列或延期释放容量。

### 2.2 释放条件

只有以下可追溯事实之一成立，承诺才释放 WIP：

1. 有效固化已经完成必要落实和验证；
2. 人明确选择无效结束；
3. 回滚已实际执行并验证完成。

证据不足本身不构成终态或释放条件；若人未另行选择 Human Closeout Gate 中的其他明确方向，
则只能继续观察或调整继续，并继续占用 WIP。

“继续观察”和“调整继续”不释放 WIP。仅创建回滚请求或把状态文字改成 `rolled_back` 也不
释放 WIP；可靠回滚能力仍须满足独立的执行与验证合同。

## 3. 首页的三个平衡维度

首页不是简单的综合分数 Top 3，也不是平均分配三个固定卡槽。它必须同时回答三个不同问题：

1. **最值得收尾**：最接近形成结论、已经到期、已有关键反证或继续占用容量收益最低的承诺。
2. **最需要解阻**：handoff 失败、缺验证合同、长期无新证据、范围或责任不清等阻塞承诺。
3. **新实践容量 / 释放容量方案**：当前还能否开始新的实践；若不能，先处理哪些既有承诺、
   缩小哪些并行范围或形成哪些终态可以释放容量。

展示规则：

- 每个维度允许为空，并明确说明为什么为空。
- 同一承诺可触发多个维度，但首页只展示一张主卡，并列出全部触发原因。
- 首页必须解释选择原因、受影响承诺和下一步；不得只显示黑盒总分或卡片数量。
- 完整事项仍保留在改进追踪与 Board，首页只提供有限注意力入口。
- 维度之间先保证覆盖，再在维度内按确定性优先级排序；不能让大量新候选淹没收尾或解阻事项。

## 4. 分阶段 WIP policy

活动阶段的 WIP 上限可在 Workspace 内配置；待决策 Inbox 和完成终态不设置活动 WIP 上限。
默认值是建议政策，不是不可越过的硬门。

用户可以有意识地超限，但 Console 必须在确认前：

- 展示将被影响或继续被挤占的既有承诺；
- 展示当时适用的分阶段上限和实际量；
- 要求填写超限原因；
- 要求填写最晚复核日期；
- 保存上述事实与人的决定来源。

超限不得静默阻塞，也不得静默放行。到达最晚复核日期后必须重新进入人的决策面；延期需要新的
可追溯决定、理由和复核日期，不能沿用旧决定或自动滚动日期。

## 5. 到期与提醒闭环

### 5.1 MVP 必须具备

Console 站内必须形成完整的到期/逾期闭环：

- 在到期前展示即将到期；
- 到期后明确标记逾期和逾期时长；
- 到期或逾期承诺进入“最值得收尾”或“最需要解阻”的确定性入口；
- 用户必须选择 Human Closeout Gate 中的一个决定，或留下新的继续/调整决定和下一复核点；
- 每次延期都形成新记录，不覆盖旧日期和旧理由；
- 页面刷新、重新进入 Console 后仍能从 Workspace 事实源恢复这些状态。

### 5.2 优先增强

下一次 Dream 或 `codex-dream` Skill 触发时，应提醒已到期、逾期或超限待复核的承诺。该能力是
优先增强，但不阻塞 MVP。V1 不做邮件、系统通知或常驻后台推送。

## 6. Human Closeout Gate

只有人能为承诺选择最终方向：

1. **有效固化**：证据支持实践，且目标载体的落实与必要验证已完成。
2. **调整继续**：保留承诺身份和历史证据，形成新版本并继续占用 `1` WIP。
3. **继续观察**：保留当前假设，记录原因和下一复核点，继续占用 `1` WIP。
4. **无效结束**：形成有证据依据的失败结论，释放 WIP，但不计入有效采纳。
5. **回滚**：创建或接续可验证的回滚流程；只有实际撤销并验证后才释放 WIP。

系统不得自动固化、自动结束、自动回滚、自动提高上限，或根据样本进度替人选择结论。每个决定
必须保存决定来源、理由、证据摘要、发生时间和当时承诺版本。

## 7. 结果展示与度量护栏

Console 必须分开展示：

- 进入试用；
- 有效固化；
- 调整继续；
- 无效结束 / 已验证回滚；
- 到期未决定。

这些是不同事件和不同质量信号，不能压成单一“闭环率”。失败是有效闭环结论，可以释放 WIP，
但不计入有效采纳；到期未决定仍是开放承诺。任何摘要都必须允许用户回到具体承诺、决定和证据。

建议保留成对流量视图，例如“进入试用 vs 形成终态”和“有效固化 vs 无效结束”，但不使用
闭环率作为催促用户尽快结束的绩效目标。

## 8. 隐私、兼容与发布边界

- 只在用户 Workspace 保存运行时承诺、提醒、决定和审计记录；仓库测试只使用合成 fixture。
- 浏览器响应和可分享工件不得包含原始消息、真实 Session 标识、绝对用户路径、私有知识正文、
  凭证或未经裁剪的 Workspace 记录。
- V1 MVP 不包括 Console 内模型、多用户审批、自动固化/结束/提高 WIP、生产架构设计、邮件或
  系统后台推送。
- 实现应优先复用 Candidate、Adoption、Validation、User Action 与 Board 投影；若现有事实源
  无法表达承诺身份、版本、到期或 override 审计，才增加最小、可迁移的确定性结构。
- 任何 Schema 或 Workspace 变化都必须提供相邻迁移与旧数据诚实降级；历史缺失值显示 unknown，
  不回填猜测。
- 本契约落库不修改 package、runtime、bundled Skill、Schema、Workspace、版本或稳定 tag。
  后续产品实现进入稳定渠道时，必须按仓库发布合同完成完整矩阵验证、推进 `product` 并创建新的
  不可变 annotated tag；不得移动 `v0.4.0`。

## 9. 稳定 Acceptance Contract

- **AC-CC-01**：Console 明确以有限改进承诺闭环为角色，并保持不调用模型、不直接改项目的边界。
- **AC-CC-02**：活动 WIP 按用户确认的实践试用承诺去重计数；同一承诺调整仍为 `1`，不同假设
  或范围并行分别计数，且只在可追溯终态后释放。
- **AC-CC-03**：首页同时覆盖最值得收尾、最需要解阻、新实践容量/释放容量方案三个维度，并
  解释选择原因；不是简单 Top 3。
- **AC-CC-04**：分阶段上限可配置，Inbox 与终态不占活动 WIP，超限是可审计软约束。
- **AC-CC-05**：每次超限记录受影响承诺、原因、最晚复核日期和当时上限/实际量；延期不能
  静默续期。
- **AC-CC-06**：Console 站内到期/逾期从提示、决策到新复核点或终态形成可恢复闭环。
- **AC-CC-07**：Human Closeout Gate 只允许人选择有效固化、调整继续、继续观察、无效结束或
  回滚；失败释放 WIP 但不计有效采纳，回滚仅在实际验证后释放。
- **AC-CC-08**：进入试用、有效固化、调整继续、无效结束/回滚、到期未决定分开展示，不以
  单一闭环率诱导草率结束。
- **AC-CC-09**：下一次 Dream/Skill 提醒作为优先增强单独验收，不阻塞 Console 站内 MVP；
  不实现邮件或后台推送。
- **AC-CC-10**：全部实现使用合成测试和隐私裁剪输出，提供迁移/兼容说明与稳定发布决策；
  不越过本契约非目标。
